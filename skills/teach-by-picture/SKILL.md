# Teach by picture

A learner who is given step after step loses the reason for the steps. Give the picture
first, then one small step that points at a part of the picture.

## Procedure
1. Name the one thing being explained, in a few words.
2. Draw it in plain text: boxes, arrows, what goes in and what comes out. Push one
   concrete example through the diagram so the arrows carry real values.
3. Say what each box is in one short line. Define each new word once, where it first
   appears.
4. Show the shapes that fit the same slot (for example, several different functions that
   can plug into the same place), so the learner sees why the design allows it.
5. Only then give the next small step, and name which box it belongs to.
6. End by asking which box is unclear. Do not ask "does that make sense?"; people say yes.

## When explaining a language feature
- Use a small generic example with unrelated names, so the learner still has to apply it
  to their own code themselves.
- Give a link or a search phrase for the full detail.

## Style
- Plain words, short sentences. No jargon the learner has not met yet.
- One picture per answer. If the learner says no picture formed, redraw a smaller one
  or a different one; do not explain the same picture again in more words.
- Show the whole system again when asked ("what is the big picture?"), including where
  the learner's current work sits in it and what is still unbuilt.
